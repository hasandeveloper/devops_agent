# HITL Remediation — Phase 1: Cancel a Runaway Query

This document explains the first remediation action the RDS Agent can take: **cancelling
a long-running query via `pg_cancel_backend`**, gated behind a human clicking
Approve/Reject on Slack buttons.

It covers:

- Why this exists and what it deliberately does not do yet
- How a candidate query gets identified and proposed
- The data model behind a remediation decision
- Setting up Slack Interactivity (in addition to the Incoming Webhook from `slack.md`)
- What happens when a human clicks Approve, Reject, or Approve All
- How the actual cancellation executes, and the safety check that runs immediately before it
- Known limitations

Read this document before changing code under:

- `app/agents/domains/rds/nodes/propose_remediation.py`
- `app/agents/tools/mcp/rds/remediation_mcp_server.py`
- `app/services/remediation_service.py`
- `app/services/slack_service.py`
- `app/controllers/webhooks.py`'s `handle_slack_interaction`
- `jobs/remediation_job.py`

Read `documentation/rds-agent/2.how-agent-pipeline-works-end-to-end.md` first if you
haven't — this document assumes you already know the diagnosis pipeline up through
`notify_slack`.

---

# 1. Why This Exists

Before this, the RDS Agent was diagnostic-only — it could tell you *what* was wrong, but
a human always had to act on it manually. `documentation/rds-agent/1.your-rds-readonly-db-role-setup.md`
explicitly called this out as a known limitation, and `IncidentStatus.awaiting_approval`/
`rejected` existed on the `Incident` model without ever being set.

This is Phase 1 of a larger, explicitly risk-ordered remediation roadmap:

```text
1. Cancel a runaway query        (pg_cancel_backend)      Low-Medium   ← this document
2. Terminate idle-in-transaction connection                Medium      (built, see doc 4)
3. Terminate a lock blocker                                Medium      (not started)
4. Scale Aurora ACU                                        Medium-High (not started)
```

(An earlier draft of this roadmap also included a simpler cancel-query variant, VACUUMing
a bloated table, instance reboot, and Aurora failover. The cancel-query variant never had
a resolved distinction from Phase 1 above and was dropped; VACUUM had no dedicated
CloudWatch alarm signal to justify it; reboot and failover were judged too drastic for
this system's per-target human-approval model to cover well. All four were removed from
the roadmap rather than left as unresolved placeholders — see `README.md`'s roadmap
table for the current, authoritative list.)

`pg_cancel_backend` was chosen first specifically because it's the lowest-risk write
action available: it interrupts the in-flight query but leaves the session alive
(unlike `pg_terminate_backend`, which drops the whole connection).

**Scope note:** this phase does not build a router that picks "which of the 8 phases
applies" to an incident. `cancel_query` is the only action type that exists — the only
judgment call `propose_remediation.py` makes is filtering *which* long-running-query
candidates are worth flagging, not choosing between remediation types. As later phases
are added, each is expected to add its own gate (a candidate-detection tool + an
LLM filter over that grounded list) rather than one central dispatcher, since an
incident can plausibly warrant more than one action type at once.

# 2. High-Level Flow

```text
persist_incident
      │
      ▼
propose_remediation          (new node — this document)
      │
      ▼
 notify_slack                (now renders Approve/Reject buttons per candidate)
      │
      ▼
      Slack
      │
      │  human clicks Approve / Reject / Approve All
      ▼
POST /webhooks/slack/interactions   (new endpoint)
      │
      ▼
Verify Slack signature
      │
      ▼
Record decision(s) in remediation_actions
      │
      ├── Rejected → done, message updated
      │
      └── Approved → enqueue execute_remediation_job (Celery)
                          │
                          ▼
                  Re-check the condition still holds
                          │
                          ▼
                    cancel_backend (write)
                          │
                          ▼
                  Update remediation_actions + Incident.status
                          │
                          ▼
                  Post result back to Slack (response_url)
```

The webhook that receives the Slack click (`POST /webhooks/slack/interactions`) and the
Celery task that actually executes the action are two separate steps, same reasoning as
the CloudWatch webhook/Celery split in document 2 — the interaction handler only does
fast Postgres bookkeeping so it can respond to Slack within its ~3 second ack window;
the actual `pg_cancel_backend` call happens afterward, in the worker.

# 3. Step 1 — Identifying a Candidate Query

None of the existing read-only tools return a live PID for a "runaway" query —
`get_performance_insights_top_sql` is aggregated/tokenized with no PID,
`get_lock_waits` only covers blocked/blocking pairs. A new read-only tool,
`get_long_running_queries`, was added to the existing `mcp_server.py` (still zero write
capability):

```text
get_long_running_queries(environment, min_duration_seconds=60)
  → [{pid, duration_seconds, query}, ...]
```

It's a plain `pg_stat_activity` query for active statements running longer than the
threshold — `REMEDIATION_LONG_QUERY_THRESHOLD_SECONDS` (default 60s), ordered by
duration descending and **capped to the 10 longest-running**, same convention as
`get_table_bloat`. Every candidate returned costs one required LLM decision and, if
flagged, one Slack block pair — uncapped, a bad-enough incident (many queries past the
threshold at once) could blow past Slack's per-message block limit or balloon the
prompt. The cap means only the 10 worst offenders are ever considered; anything beyond
that isn't proposed at all.

# 4. Step 2 — Deciding What to Propose

`propose_remediation.py` runs right after `persist_incident`, before `notify_slack`:

```text
propose_remediation
      │
  risk_tier == "low"?           ──Yes──▶ stop, remediation: None
      │ No
  alarm state == "ALARM"?       ──No───▶ stop, remediation: None
      │ Yes
  get_long_running_queries
      │
  any candidates?                ──No──▶ stop, remediation: None
      │ Yes
  LLM: one {pid, should_propose, rationale} per candidate
      │
  pid valid AND should_propose?  ──No──▶ drop (logged if pid was hallucinated)
      │ Yes
  create one RemediationAction row per approved candidate
      │
      ▼
  notify_slack
```

1. **Skipped entirely if `diagnosis.risk_tier == "low"`** — no point proposing action on
   an informational alarm.
2. **Skipped entirely if the triggering alarm's own state isn't `"ALARM"`** (e.g. a
   `NewStateValue: "OK"` notification for an alarm that already resolved). CloudWatch
   sends a notification on *every* state transition, including back to OK — without this
   check, a resolved alarm's own diagnosis pipeline can still run to completion and
   propose cancelling connections that are, by definition, no longer the live problem.
   Confirmed live: a second, unrelated alarm's "Resolved" pipeline run re-proposed pids
   that a *different* alarm's remediation had already terminated moments earlier.
3. Calls `get_long_running_queries`. No candidates → `{"remediation": None}`, no change
   from today's behavior.
4. If candidates exist, calls an LLM with structured output
   (`RemediationProposal` — one `{pid, should_propose, rationale}` entry **required per
   candidate offered**). The model's job is filtering (e.g. don't flag what's obviously
   a backup or an explicit `VACUUM`) and explaining, never inventing a PID.
5. **Every returned `pid` is validated against the candidate list before being trusted**
   — same belt-and-suspenders spirit as `mcp_server.py`'s `_explain_safety_violation`.
   A hallucinated pid is logged and dropped, not acted on.
6. Each `should_propose=True` decision becomes its **own** `RemediationAction` row — a
   cluster with three flagged queries produces three independently-approvable rows, not
   one bundled decision.

# 5. Data Model — `remediation_actions`

One row per candidate action, added in migration `0003`:

| Column | Purpose |
|---|---|
| `incident_id` | Which incident this belongs to (an incident can have many) |
| `action_type` | `"cancel_query"` today — a plain string, not a DB enum, so later phases don't need an `ALTER TYPE` migration each time |
| `target_pid`, `target_query`, `target_duration_seconds` | Snapshot at proposal time — used for the Slack message *and* as the re-check baseline at execution time |
| `rationale` | Why the LLM flagged it — shown to the human approver |
| `status` | `proposed → approved/rejected → executed/failed` |
| `slack_response_url` | Slack's short-lived (~30 min / a handful of uses) URL for updating the message after a decision |
| `decided_by` | Who clicked the button |
| `result` | Outcome text — `"cancelled"`, `"skipped: <reason>"`, or an error string |

`Incident.status` is derived from its rows via `recompute_incident_status` (see
`app/services/remediation_service.py`): `awaiting_approval` while anything is still
pending a decision or execution; `resolved` once nothing is pending and at least one row
executed; `rejected` only if every row was rejected. A partially-approved incident (some
rows rejected, some approved) settles to `resolved` once its approved rows finish — the
human addressed what needed addressing.

# 6. Slack Setup — Enabling Interactivity

`documentation/devops/slack/slack.md` covers creating the Incoming Webhook
(`SLACK_WEBHOOK_URL`) this project already posts diagnoses to. Receiving a button click
back needs two more things on the **same** Slack app:

1. **Interactivity & Shortcuts** (left sidebar of the app's settings) → toggle on →
   **Request URL** = `https://<your-host>/webhooks/slack/interactions` (use the ngrok
   URL locally, per the project's ngrok setup doc, or your real domain in production).
2. **Basic Information** → **App Credentials** → copy **Signing Secret** →
   `SLACK_SIGNING_SECRET` in `.env`.

No bot token, no OAuth scopes — posting still goes through the plain Incoming Webhook,
and updating the message after a click uses the click payload's own `response_url`, not
`chat.update`/`chat:write`.

**`SLACK_SIGNING_SECRET` is required, not optional**, once this endpoint is live —
unlike `verify_github_signature` (which treats a blank secret as "verification
disabled"), `verify_slack_signature` treats a blank secret as a hard `401`, since this
endpoint can trigger a real write action.

# 7. Step 3 — The Slack Message

`app/services/slack_service.py` renders one section + button pair per still-`proposed`
row:

```text
PID: 1234
Duration: 8m 32s
Query: SELECT ...

Reason:
This query has been running significantly longer
than the configured threshold.

[Approve]  [Reject]
```

Already-decided rows render as static status text instead (`✅ cancelled`,
`❌ rejected by @alice`, `⏳ approved, executing…`, `⚠️ cancellation failed: ...`) — no
buttons, so a partially-decided incident shows history, not just what's left pending. A
trailing **"Approve All Remaining"** button appears while at least one row is still
pending.

---

# 8. Step 4 — Receiving the Click

`POST /webhooks/slack/interactions` → `handle_slack_interaction`:

1. Verifies the request signature (`v0=` HMAC-SHA256 over `v0:{timestamp}:{raw_body}`,
   plus a 5-minute replay window) — mirrors `verify_github_signature`'s pattern.
2. Parses the `payload` form field, branches on `action_id`:
   - `approve_remediation` / `reject_remediation` (value = remediation id): records the
     decision on that one row; approval enqueues `execute_remediation_job`.
   - `approve_all_remediations` (value = incident id): approves every still-`proposed`
     row for the incident, enqueuing one execution job per row.
   - A double-click (a row that isn't `proposed` anymore) is a no-op, not an error.
3. Rebuilds and posts the **entire** message via `response_url` — because
   `response_url` replaces the whole message, every update re-renders every row from
   its current DB state, not just the one that was clicked.

Query evidence (the exact SQL from `get_performance_insights_top_sql`/
`explain_query_for_pid`) is **not** included in re-rendered messages — it was never
persisted on the incident (see `AgentState.query_evidence`'s docstring), so it
disappears from the message after the first update. This is an accepted display
tradeoff, not a bug.

# 9. Step 5 — Executing an Approved Action

`jobs/remediation_job.py::execute_remediation_job(remediation_id)` — one Celery task per
approved row, so approving 3 of 5 flagged PIDs fans out into 3 independent tasks.

The actual write happens in a **separate** MCP stdio server,
`remediation_mcp_server.py` — deliberately apart from the read-only `mcp_server.py`, so
that file's "never exposes a mutating boto3 call" invariant stays literally true. It
connects using the `devops_agent_remediation` role (Section 7 of document 1), not
`devops_agent_readonly`.

## 9.1 The Re-Check-Before-Acting Safety Step

Approval happens at human speed — seconds to minutes after proposal. By execution time,
the original problem may have already resolved itself (the query finished normally), or
the pid may have been reused by an unrelated, newer backend. `cancel_backend` re-reads
`pg_stat_activity` for that pid immediately before calling `pg_cancel_backend` and checks:

1. The pid is still present.
2. It's still `state = 'active'`.
3. Its query text still matches `target_query` (guards the pid-reuse case).

If any check fails, it returns `{"action_taken": False, "skipped": "<reason>"}` instead
of cancelling — treated as a successful no-op (`status = executed`, `result = "skipped:
..."`), not a failure, since the incident already looks resolved.

**This re-check pattern is meant to generalize** to every future phase, not just
cancel-query — Phase 2 must re-check the connection is still idle-in-transaction (it
does, see doc 4), Phase 3 that the block still exists, Phase 4 that the database is
still pinned at its capacity ceiling before raising it. The shape (`recheck → act →
record the actual outcome`) is what each future action type's tool is expected to
implement.

## 9.2 No Automatic Retry

`execute_remediation_job` has no Celery retry configured. A failed `cancel_backend` call
is recorded as `status = failed` on the row (visible in the final Slack message), not
retried — retrying risks attempting to cancel a pid a second time after conditions have
changed again, exactly the TOCTOU risk the re-check above exists to avoid.

## 9.3 `response_url` Exhaustion Fallback

Confirmed live during testing, not just theoretical: approving 7 candidates via "Approve
All Remaining" fanned out into 7 execution jobs, each posting its own update through the
*same* `response_url` from the original click. The 7th (slowest) completion got a plain
`404` from Slack — `response_url` really is capped at a handful of uses, and Slack does
not degrade gracefully once it's exhausted.

Because `mark_remediation_result`/`recompute_incident_status` both run *before* the Slack
post in `execute_remediation_job`, the 404 cost nothing correctness-wise — the pid really
was cancelled, the row really was marked `executed`. Only the message itself went stale.

The fix: `post_remediation_update` now returns whether it actually succeeded. If it
didn't, and every row for that incident has reached a terminal state
(`executed`/`failed`/`rejected` — nothing left `proposed`/`approved`), `execute_remediation_job`
posts one fresh message via `SLACK_WEBHOOK_URL` (a durable channel post, not the
exhausted `response_url`) so a large batch always ends with an accurate final message.
This only fires on failure — the normal small-batch case is unchanged, no extra message.
In a very large batch, more than one tail-end completion could independently satisfy
this and post a duplicate final message; accepted as rare and harmless rather than
adding cross-task locking for it.

# 10. Known Limitations

- **Only `cancel_query` exists.** No cross-phase router — see the scope note in Section 1.
- **`response_url` limits, mitigated but not eliminated.** See §9.3 — a large approval
  batch now gets a guaranteed accurate final message via a fallback channel post, but a
  very large batch could rarely post that fallback more than once.
- **Query evidence doesn't survive a re-render** (Section 8) — not persisted on the
  incident.
- **No modal / stateful multi-select.** "Approve All Remaining" is a convenience
  shortcut, not a checkbox-based selection UI — see Section 7.
