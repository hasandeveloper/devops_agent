# Database Role Setup

Run the following commands **once per environment**.

For example:

```text
DEV        → Run on DEV RDS
STAGING    → Run on STAGING RDS
PRODUCTION → Run on PRODUCTION RDS
```

Connect to the environment's application database as a PostgreSQL administrator/superuser.

The application itself should never run these commands.

These are manual database setup commands.

---

## 1. Create the Read-Only Role

Create the role on the environment's RDS cluster:

```sql
CREATE ROLE devops_agent_readonly
WITH LOGIN PASSWORD '<pick-a-real-password>';
```

Use a separate password for each environment.

For example:

```text
DEV:
devops_agent_readonly / <DEV password>

STAGING:
devops_agent_readonly / <STAGING password>

PRODUCTION:
devops_agent_readonly / <PRODUCTION password>
```

If the role already exists in that environment, do not create it again.

---

## 2. Grant Database Monitoring Access

Grant access to PostgreSQL statistics:

```sql
GRANT pg_read_all_stats TO devops_agent_readonly;
```

This allows the RDS Agent to see database monitoring information such as:

* Active connections
* Running queries
* Locks
* PostgreSQL statistics

Without this permission, a normal PostgreSQL user has limited visibility into other database sessions.

Because every environment has its own RDS cluster, this permission must be granted separately in each environment.

---

## 3. Grant Schema Access

Connect to the application's database for that environment and grant access to the required schemas:

```sql
GRANT USAGE ON SCHEMA public
TO devops_agent_readonly;

GRANT USAGE ON SCHEMA pgboss
TO devops_agent_readonly;
```

Schema access is required before PostgreSQL allows the user to access tables inside those schemas.

---

## 4. Grant Read Access to Existing Tables

Grant `SELECT` access to the existing tables:

```sql
GRANT SELECT ON ALL TABLES IN SCHEMA public
TO devops_agent_readonly;

GRANT SELECT ON ALL TABLES IN SCHEMA pgboss
TO devops_agent_readonly;
```

This allows the RDS Agent to read the required application tables.

It does not allow the agent to modify the data.

---

## 5. Grant Read Access to Future Tables

The previous `GRANT SELECT ON ALL TABLES` commands apply to tables that already exist.

If a future migration creates a new table, the read-only user will not automatically receive access to that table.

To handle future tables, run:

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT ON TABLES
TO devops_agent_readonly;

ALTER DEFAULT PRIVILEGES IN SCHEMA pgboss
GRANT SELECT ON TABLES
TO devops_agent_readonly;
```

This ensures that future tables created under the relevant database owner's default privileges also receive the required read access.

---

## 6. Configure the Environment Credentials

After the PostgreSQL role has been created and the required permissions have been granted, add the read-only credentials to the environment configuration.

For example:

### DEV

```text
DB_DEV_HOST=<DEV RDS endpoint>
DB_DEV_PORT=5432
DB_DEV_DATABASE=<DEV database>
DB_DEV_READONLY_USERNAME=devops_agent_readonly
DB_DEV_READONLY_PASSWORD=<DEV password>
```

### STAGING

```text
DB_STAGING_HOST=<STAGING RDS endpoint>
DB_STAGING_PORT=5432
DB_STAGING_DATABASE=<STAGING database>
DB_STAGING_READONLY_USERNAME=devops_agent_readonly
DB_STAGING_READONLY_PASSWORD=<STAGING password>
```

### PRODUCTION

```text
DB_PRODUCTION_HOST=<PRODUCTION RDS endpoint>
DB_PRODUCTION_PORT=5432
DB_PRODUCTION_DATABASE=<PRODUCTION database>
DB_PRODUCTION_READONLY_USERNAME=devops_agent_readonly
DB_PRODUCTION_READONLY_PASSWORD=<PRODUCTION password>
```

The RDS Agent uses these settings when it needs to connect to the application's database.

Do not put these credentials in the application's normal database fields.

Use:

```text
DB_*_READONLY_USERNAME
DB_*_READONLY_PASSWORD
```

for the RDS Agent.

Do not use the application's normal:

```text
DB_*_USERNAME
DB_*_PASSWORD
```

credentials if those belong to a full-access database user.

# After Setup: How the RDS Agent Works

Once the role, permissions, and environment configuration are set up, the RDS Agent can use the same agent code across all environments.

The important point is:

> **The agent is shared, but the database connection is environment-specific.**

The agent does not create a new agent for DEV, STAGING, or PRODUCTION.

Instead, it selects the correct database configuration based on the environment associated with the event.

---

## 1. An Event Reaches the RDS Agent

For example, suppose a database issue occurs in DEV.

The event contains the environment information:

```text
environment = dev
```

The RDS Agent receives the event and knows that it needs to investigate the DEV environment.

The flow is:

```text
Database Event
      │
      ↓
RDS Agent
      │
      ↓
environment = dev
```

---

## 2. The Agent Selects the Correct Database Configuration

The agent uses the environment to select the correct configuration.

For DEV:

```text
environment = dev
        ↓
DB_DEV_*
```

For STAGING:

```text
environment = staging
        ↓
DB_STAGING_*
```

For PRODUCTION:

```text
environment = production
        ↓
DB_PRODUCTION_*
```

Conceptually:

```text
Environment
     │
     ├── dev ───────────────→ DB_DEV_*
     │
     ├── staging ───────────→ DB_STAGING_*
     │
     └── production ────────→ DB_PRODUCTION_*
```

The agent must never guess the environment.

---

## 3. The Agent Connects Using the Read-Only Credentials

Suppose the event is from DEV.

The agent loads:

```text
DB_DEV_HOST
DB_DEV_PORT
DB_DEV_DATABASE
DB_DEV_READONLY_USERNAME
DB_DEV_READONLY_PASSWORD
```

It then creates a database connection to the DEV RDS database:

```text
RDS Agent
    │
    ↓
DEV database configuration
    │
    ↓
DEV RDS
    │
    ↓
DEV Database
    │
    ↓
devops_agent_readonly
```

For a STAGING event, the same agent instead uses:

```text
DB_STAGING_*
```

and connects to the STAGING RDS database.

---

## 4. The Agent Runs Diagnostic Tools

After connecting to the correct database, the RDS Agent can run its database diagnostic tools.

For example:

```text
get_active_connections()
```

can inspect active database connections.

```text
get_lock_waits()
```

can inspect lock waits.

```text
explain_query_for_pid()
```

can inspect the execution plan for a query.

```text
get_table_bloat()
```

can inspect table bloat/statistics.

These tools use the `devops_agent_readonly` connection.

---

## 5. The Agent Cannot Modify the Database

The database connection uses:

```text
devops_agent_readonly
```

Therefore, the agent is restricted to the permissions granted to that role.

For example:

```text
Agent
  │
  ├── SELECT data              → Allowed
  ├── Read pg_stat_activity    → Allowed
  ├── Read pg_locks            → Allowed
  ├── Run diagnostics          → Allowed
  │
  ├── INSERT                   → Not allowed
  ├── UPDATE                   → Not allowed
  ├── DELETE                   → Not allowed
  ├── DROP TABLE               → Not allowed
  ├── ALTER TABLE              → Not allowed
  └── CREATE ROLE              → Not allowed
```

This keeps the investigation process read-only.

---

# Complete Runtime Flow

The complete flow looks like this:

```text
                         Event
                           │
                           ↓
                    ┌─────────────┐
                    │  RDS Agent  │
                    └──────┬──────┘
                           │
                           ↓
                 Identify Environment
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ↓             ↓             ↓
            DEV         STAGING         PROD
             │             │             │
             ↓             ↓             ↓
        DB_DEV_*      DB_STAGING_*   DB_PRODUCTION_*
             │             │             │
             ↓             ↓             ↓
          DEV RDS       STAGING RDS     PROD RDS
             │             │             │
             ↓             ↓             ↓
        Read-Only      Read-Only       Read-Only
          User            User            User
             │             │             │
             └─────────────┼─────────────┘
                           │
                           ↓
                   Run Diagnostic Tools
                           │
                           ↓
                    Analyze the Issue
                           │
                           ↓
                      Diagnosis
```

The important part is that **only one agent is running the logic**. The database connection changes according to the environment.

---

# Why This Architecture Is Used

This approach gives us:

### One Agent

There is one RDS Agent implementation.

We do not maintain separate agents for:

```text
RDS Agent DEV
RDS Agent STAGING
RDS Agent PROD
```

Instead, we have:

```text
RDS Agent
```

with environment-specific database connections.

### Environment Isolation

Although the agent is shared, the databases remain isolated:

```text
DEV Agent Connection
    ↓
DEV RDS only

STAGING Agent Connection
    ↓
STAGING RDS only

PROD Agent Connection
    ↓
PROD RDS only
```

A DEV database credential cannot be used to access the STAGING or PRODUCTION RDS cluster.

### Consistent Diagnostics

All environments use the same tools:

```text
get_active_connections()
get_lock_waits()
explain_query_for_pid()
get_table_bloat()
```

Therefore, database diagnostics behave consistently across DEV, STAGING, and PRODUCTION.

# HITL and Database Access

Human-in-the-loop (HITL) is separate from database connectivity.

HITL does not give the agent database access.

The read-only PostgreSQL role controls what the agent can read.

HITL controls whether the agent needs human approval before performing an action.

## Current Flow

Currently, the RDS Agent is focused on investigation and diagnosis:

```text
Event
  │
  ↓
RDS Agent
  │
  ↓
Identify Environment
  │
  ↓
Select Environment DB Configuration
  │
  ↓
Connect Using Read-Only Credentials
  │
  ↓
Gather Database Information
  │
  ↓
Diagnose Problem
  │
  ↓
Return Diagnosis
```

## Future Flow With HITL

If remediation actions are added later:

```text
Event
  │
  ↓
RDS Agent
  │
  ↓
Identify Environment
  │
  ↓
Connect Using Read-Only Credentials
  │
  ↓
Investigate
  │
  ↓
Generate Diagnosis
  │
  ↓
Potential Action
  │
  ↓
HITL Approval
  │
  ├── Rejected → Stop
  │
  └── Approved
          │
          ↓
      Execute Action
```

HITL therefore controls **actions**, not normal read-only database investigation.

# Verification

After setting up the role, verify that it has the expected permissions.

For DEV:

```python
import psycopg
from config.settings import settings

conn = psycopg.connect(
    host=settings.db_dev_host,
    port=settings.db_dev_port,
    dbname=settings.db_dev_database,
    user=settings.db_dev_readonly_username,
    password=settings.db_dev_readonly_password,
)

cur = conn.cursor()
```

For STAGING or PRODUCTION, use the corresponding environment configuration.

---

## Verify the Role

Run:

```python
cur.execute("""
    SELECT
        rolcanlogin,
        rolsuper,
        rolcreaterole,
        rolcreatedb
    FROM pg_roles
    WHERE rolname = 'devops_agent_readonly'
""")

print(cur.fetchone())
```

Expected result:

```text
(True, False, False, False)
```

This means:

```text
Can login       → Yes
Superuser       → No
Create roles    → No
Create database → No
```

---

## Verify `pg_read_all_stats`

Run:

```python
cur.execute("""
    SELECT r.rolname
    FROM pg_auth_members m
    JOIN pg_roles r ON r.oid = m.roleid
    JOIN pg_roles u ON u.oid = m.member
    WHERE u.rolname = 'devops_agent_readonly'
""")

print(cur.fetchall())
```

Expected result:

```text
[('pg_read_all_stats',)]
```

---

## Verify Table Permissions

Run:

```python
cur.execute("""
    SELECT
        table_schema,
        count(*)
    FROM information_schema.role_table_grants
    WHERE grantee = 'devops_agent_readonly'
    GROUP BY table_schema
""")

print(cur.fetchall())
```

This shows how many tables the read-only role can access in each schema.

# Adding a New Environment

When a new environment is created, repeat the database role setup on that environment's RDS cluster.

For example:

```text
1. Connect to the environment's RDS database
2. Create devops_agent_readonly
3. Grant pg_read_all_stats
4. Grant schema access
5. Grant SELECT on existing tables
6. Configure default privileges
7. Add environment-specific read-only credentials
8. Verify the permissions
```

The RDS Agent code does not need to be duplicated.

Only the environment-specific database configuration and database permissions need to be added.

---

# Known Limitations / Not Done Here

* **Manual setup:** Database role setup is currently manual and must be performed for each environment.
* **Password rotation:** No automated password rotation process is currently documented.
* **Environment isolation:** DEV, STAGING, and PRODUCTION use separate RDS clusters and separate read-only credentials.
* **Read-only access:** The `devops_agent_readonly` role is intended for investigation and diagnostics only.
* **No remediation:** The current database role does not provide write access for remediation.
* **HITL:** HITL can be introduced later for actions that require human approval. It does not change the read-only database access model.
