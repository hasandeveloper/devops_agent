# HITL Remediation — Phase 2: Disconnect an Idle-in-Transaction Connection

This document covers what's different about Phase 2 relative to Phase 1. Read
`documentation/rds-agent/3.hitl-remediation-phase-1-cancel-query.md` first — the
approval flow, the `remediation_actions` table's shared columns, Slack's Interactivity
setup, `response_url`'s exhaustion fallback, and the no-automatic-retry rule are all
identical between the two phases and not repeated here.

---

# 1. Why Terminate, Not Cancel

An idle-in-transaction connection has no query running — there's nothing for
`pg_cancel_backend` to interrupt. The only way to release whatever lock it's holding is
to end the session with `pg_terminate_backend`. That's a heavier action than Phase 1's:
it drops the whole connection, not just its current statement.

---

# 2. The Two-Part Gate

Unlike Phase 1's single condition (duration past a threshold), this phase requires two
things to both be true before a connection is even shown to a human:

1. Idle-in-transaction longer than `REMEDIATION_IDLE_CONNECTION_THRESHOLD_SECONDS`
   (default 300s — deliberately higher than Phase 1's 60s, since termination is more
   disruptive).
2. **Confirmed to actually be blocking another query right now** — cross-referenced
   against `blocking_pid` values in `context.lock_waits`, which `gather_context.py`
   already fetched. No new tool call needed for this half.

Duration alone is deliberately not enough. A connection idle for a few seconds between
statements is normal application behavior; only a sustained one that's demonstrably
causing harm is worth a human's attention, given how much more disruptive termination
is than cancellation.

`get_idle_in_transaction_connections` (in `mcp_server.py`, still read-only) supplies the
duration half; `propose_idle_connection_remediation.py` does the cross-referencing
against lock waits before anything reaches the LLM filter step. The LLM's job is
narrower than Phase 1's too — every candidate it sees has already been confirmed to be
blocking something; it's filtering for "does this still look like an abandoned session
worth terminating," not deciding whether it's causing harm in the first place.

---

# 3. Data Model — One New Column

`remediation_actions` gains `target_backend_start` (nullable `Float`, epoch seconds) —
only Phase 2 populates it; Phase 1 rows leave it `NULL`.

**Why a Float, not a timestamp column:** a raw `datetime` isn't natively
JSON-serializable over the MCP round-trip, the exact same class of bug that broke
`target_duration_seconds` before its `::float8` cast was added (see doc 3 §3 and this
column's own comment in `mcp_server.py`). Casting to epoch seconds in SQL — the same
fix already proven for duration — sidesteps the whole bug category instead of
reproducing it. Confirmed empirically before this ever shipped: a synthetic
idle-in-transaction session's `backend_start` round-trips through the tool call as a
plain Python `float`, fully JSON-serializable.

---

# 4. The Stronger Recheck

`cancel_backend`'s recheck (pid present, still active, query text matches) isn't strong
enough here, because a wrong guess costs more: dropping a whole connection instead of
interrupting one query. `terminate_backend` adds a fourth check on top of the
equivalent three:

1. Pid still present.
2. Still `state = 'idle in transaction'` (not `'active'` — this is the one Phase-specific
   difference from Phase 1's state check).
3. Query text still matches the snapshot (`_query_still_matches`, reused as-is).
4. **`backend_start` still matches** (`_backend_start_still_matches`, new) — a
   connection's start timestamp never changes for its lifetime, so this is a firmer
   identity fingerprint than query text alone. Query text could theoretically
   coincidentally match a different, newer connection that reused the same pid;
   `backend_start` essentially can't.

All four have to pass before `pg_terminate_backend` is called. Any single failure
returns `{"action_taken": false, "skipped": "<reason>"}` — recorded as `executed` with a
`skipped:` result, not a failure, exactly like Phase 1's equivalent case.

Verified live against the real dev cluster: a synthetic idle-in-transaction session was
correctly terminated (confirmed gone from `pg_stat_activity` afterward, not just a
client-side assumption), and a second call against the same, now-gone pid correctly
skipped rather than erroring.

# 5. Slack Copy

Reusing Phase 1's generic buttons and wording here would understate what's actually
about to happen. `slack_service.py`'s `_ACTION_COPY` table branches purely on
presentation, keyed by `action_type`:

- Button reads **"Terminate Connection"**, not "Approve."
- The pending-row text adds an explicit line: *"This will drop the connection entirely
  — the client will need to reconnect."*
- The duration label reads "Idle for" instead of "Duration."

The underlying `action_id`s (`approve_remediation`/`reject_remediation`) are unchanged
from Phase 1 — `handle_slack_interaction` needed zero code changes, since approval
routing is generic by row id, not by action type.

---

# 6. Execution Dispatch

`jobs/remediation_job.py` no longer hardcodes `cancel_backend`. A small
`_ACTION_HANDLERS` dict maps `action_type` → `{tool, verb, build_args}`:

```python
_ACTION_HANDLERS = {
    "cancel_query": {"tool": "cancel_backend", "verb": "cancelled", "build_args": ...},
    "terminate_idle_connection": {"tool": "terminate_backend", "verb": "terminated", "build_args": ...},
}
```

This is the one place in the codebase that needs to know about every remediation action
type. The graph, Slack rendering, and the interaction handler all stay generic by row
id — a future Phase 3 means one more dict entry here, not new branching logic
elsewhere.

---

# 7. Graph Wiring

One more node, sequential, same shape as Phase 1's own insertion:

```text
persist_incident → propose_remediation → propose_idle_connection_remediation → notify_slack
```

`propose_idle_connection_remediation` reads whatever `propose_remediation` already put
in `state["remediation"]` (possibly `None`, possibly a list of Phase 1 candidates) and
returns the union — plain Python list concatenation, no LangGraph reducer needed, since
the nodes run sequentially rather than in parallel.

# 8. Why There's No CloudWatch Alarm Feeding This Phase Directly

Unlike Phase 1 (an alarm about CPU/connections naturally correlates with a runaway
query), there is **no native CloudWatch metric for idle-in-transaction connection
count** at all — this is a genuine gap in AWS's own RDS/Aurora monitoring, not
something missing from this app.

- **`DatabaseConnections`** is a raw total count with no breakdown by session state —
  active, idle, and idle-in-transaction all look identical on that graph.
- **Performance Insights doesn't catch it either.** PI measures Database Load (Average
  Active Sessions) — a session only counts toward that if it's actively doing
  something. An idle-in-transaction session is, by definition, doing nothing, so it
  contributes zero load. It can sit there for hours holding a lock and blocking real
  work while PI's dashboard shows a perfectly flat, healthy-looking line the entire
  time. This is precisely why `get_idle_in_transaction_connections` has to query
  `pg_stat_activity` directly rather than reading anything AWS already computes.

**Two real ways to get an actual CloudWatch alarm for this anyway, if wanted:**

1. **Log-based.** Enable `log_lock_waits` (+ `deadlock_timeout`) in the DB parameter
   group, export Postgres logs to CloudWatch Logs, and create a CloudWatch Logs metric
   filter counting the lock-wait log pattern. Alarm on that derived metric normally.
   Since it's a real CloudWatch alarm delivered via SNS, it flows through the exact
   same `/webhooks/cloudwatch` pipeline as every other alarm — no new integration
   needed on this app's side.
2. **Custom metric.** A small scheduled job (Lambda on an EventBridge schedule, or a
   cron script) running the same kind of query this phase's tool does, pushing the
   count to CloudWatch via `put_metric_data`. Once that metric exists, alarm on it like
   any built-in one. Real new infrastructure to build and run, not a config toggle.

**The practical point, though: you may not actually need a dedicated alarm for this at
all.** Phase 2's gate doesn't wait for a specific "idle connection" alarm — it runs on
any alarm that produces a non-low-risk diagnosis, whatever triggered it (CPU,
connections, memory, whatever you already have configured). So if a CPU or connections
alarm fires and there happens to be a blocking idle-in-transaction connection at that
moment, Phase 2's check already runs as part of that same incident, no dedicated alarm
required. A dedicated alarm would only add value by catching this specifically when
nothing else is alarming — i.e., a case where idle-in-transaction blocking is happening
in isolation, with CPU/connections/memory all still looking fine.

# 9. Known Limitations

- Same `response_url` exhaustion caveat as Phase 1 (see doc 3 §9.3) — the fallback
  channel-post mechanism is shared, not reimplemented.
- The two-part gate's "confirmed blocking" check only looks at `context.lock_waits` as
  captured once at the start of the incident's investigation — it isn't re-checked
  between proposal and the LLM filter step (only right before execution, via
  `terminate_backend`'s own recheck).
- No escalation path yet from a failed Phase 1 cancel to a Phase 2 terminate, or vice
  versa — each phase's proposal is independent, as designed.
- No dedicated CloudWatch alarm exists for the condition this phase targets — see §8.
