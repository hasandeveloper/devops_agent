````md
# RDS Diagnosis Pipeline — End to End

This document explains how the **RDS Agent processes a CloudWatch alarm from start to finish**.

It covers:

- How an alarm reaches the application
- How the event is stored
- How Celery processes the event
- How the RDS Agent gathers database information
- How the agent investigates the problem
- How the LLM creates a diagnosis
- How the incident is stored
- How the diagnosis is sent to Slack
- What happens when something fails
- Where logs are stored
- Current limitations

Read this document before changing code under:

- `app/agents/domains/rds/`
- `app/agents/tools/mcp/rds/mcp_server.py`
- `jobs/webhooks_job.py`
- `config/celery_app.py`
- `config/logging.py`

---

# 1. High-Level Flow

The complete flow looks like this:

```text
CloudWatch Alarm
      │
      ▼
     SNS
      │
      ▼
POST /webhooks/cloudwatch
      │
      ▼
Rate Limit Check
      │
      ▼
SNS Signature Verification
      │
      ▼
Store Event in raw_events
      │
      ▼
Send Job to Celery
      │
      │
      │  Webhook finishes here
      │
      ▼
────────────────────────────────────
       Celery Worker
────────────────────────────────────
      │
      ▼
supervisor.route()
      │
      ▼
RDS Agent
      │
      ▼
gather_context
      │
      ▼
retrieve_similar_incidents
      │
      ▼
investigate_further
      │
      ▼
diagnose
      │
      ▼
persist_incident
      │
      ▼
notify_slack
      │
      ▼
Slack
````

The important point is that **the webhook and the diagnosis pipeline are not running in the same process**.

The FastAPI application receives the CloudWatch notification, stores it, and sends a job to Celery.

The Celery worker does the expensive work:

* AWS API calls
* Database queries
* Vector searches
* LLM calls
* Incident creation
* Slack notification

This keeps the webhook fast and prevents a slow diagnosis from blocking the HTTP request.

---

# 2. Step 1 — CloudWatch Sends the Alarm

When a CloudWatch alarm is triggered:

```text
CloudWatch
    │
    ▼
SNS
```

SNS sends a notification to:

```text
POST /webhooks/cloudwatch
```

The endpoint is implemented in:

```text
app/controllers/webhooks.py
```

The webhook does not perform the diagnosis itself.

Its job is only to safely receive and store the event and submit it to Celery.

---

# 3. Step 2 — Webhook Receives the Event

The webhook performs several checks and operations.

## 3.1 Rate Limit Check

The first check is the webhook rate limit.

The application uses Redis to limit how many requests can reach the webhook within a time window.

The relevant configuration is:

```text
WEBHOOK_RATE_LIMIT
WEBHOOK_RATE_LIMIT_WINDOW_SECONDS
```

The default is:

```text
60 requests / 60 seconds
```

The purpose is to protect the application from:

* Too many CloudWatch notifications
* Accidental event floods
* Malicious request floods

The rate limiter uses Redis:

```text
config/redis_client.py
config/reliability/rate_limiter.py
```

The current implementation uses a fixed time window with:

```text
INCR
EXPIRE
```

It is not a sliding-window rate limiter.

---

# 4. Step 3 — SNS Verification

After the rate-limit check, the application verifies the SNS request.

This includes:

* SNS signature verification
* Subscription confirmation handling
* SNS control messages

The relevant code is:

```text
handle_sns_control_message
```

Only valid SNS notifications should continue to the diagnosis pipeline.

---

# 5. Step 4 — Store the Raw Event

The notification is stored in the database using:

```text
store_raw_event(...)
```

This creates a record in:

```text
raw_events
```

The raw event is important because it provides a permanent record that the notification was received.

For example:

```text
CloudWatch Alarm
       │
       ▼
     SNS
       │
       ▼
  raw_events
```

Even if the Celery worker is down, the event has already been stored.

The event can therefore remain in the database with:

```text
processed = false
```

until it is successfully processed.

---

# 6. Step 5 — Send the Event to Celery

After storing the event, the webhook creates a Celery task:

```python
aws_sns_event_job.delay(...)
```

The job is placed into the Celery/Redis queue.

The webhook then returns the HTTP response.

At this point:

```text
Webhook processing = finished
```

The actual diagnosis has not happened yet.

Everything after this point runs inside the Celery worker.

---

# 7. Step 6 — Celery Processes the Job

The Celery task is defined in:

```text
jobs/webhooks_job.py
```

The task calls:

```python
supervisor.route(raw_event)
```

The Celery task also has retry handling.

The current task configuration allows:

```text
Maximum retries: 3
Retry delay: 30 seconds
```

---

# 8. Celery Rate Limit

There are two different rate limits in the system.

## Webhook rate limit

Protects the HTTP endpoint:

```text
CloudWatch
    │
    ▼
Webhook
    │
    ▼
Rate limit
```

## Celery rate limit

Protects the diagnosis pipeline:

```text
Celery Queue
    │
    ▼
Celery Worker
    │
    ▼
RDS Diagnosis
```

The Celery rate limit is configured through:

```text
CELERY_TASK_RATE_LIMIT
```

The current default is:

```text
20 tasks / minute
```

These two limits are independent.

---

# 9. Retry Behaviour

Not every failure should be retried.

The current behaviour is:

| Error                   | Retry? | Reason                                      |
| ----------------------- | ------ | ------------------------------------------- |
| `NotImplementedError`   | No     | The required domain agent does not exist    |
| `ValueError`            | No     | The event/namespace is not supported        |
| `TokenBudgetExceeded`   | No     | The investigation exceeded its token budget |
| `asyncio.TimeoutError`  | Yes    | Could be a temporary timeout                |
| `GraphRecursionError`   | Yes    | Currently falls into the generic retry path |
| Other unexpected errors | Yes    | Could be a temporary failure                |

Unexpected errors are retried up to:

```text
3 times
```

with:

```text
30 seconds
```

between retries.

# 10. Step 7 — Supervisor Selects the Agent

The supervisor is responsible for deciding which domain agent should process the event.

Code:

```text
app/agents/supervisor.py
```

For example:

```text
AWS/RDS
    │
    ▼
RDS Agent
```

Other namespaces may eventually route to:

```text
ECS Agent
ALB Agent
CI/CD Agent
```

The supervisor does not use an LLM.

It uses deterministic rules based on information in the event.

This makes routing predictable.

The RDS agent is implemented under:

```text
app/agents/domains/rds/
```

The main graph is created in:

```text
app/agents/domains/rds/builder.py
```

The graph contains these steps:



# 12. Step 9 — Gather Context

The first RDS step is:

```text
gather_context
```

This step does not use an LLM.

It collects information needed to understand the database problem.

The RDS MCP server provides tools for things such as:

* RDS cluster information
* Recent metric trends
* Environment information
* Active database connections
* Lock waits

The MCP server is:

```text
app/agents/tools/mcp/rds/mcp_server.py
```

---

# 13. Database Connection

Some RDS tools need to connect directly to the application's database.

Examples include:

```text
get_active_connections
get_lock_waits
explain_query_for_pid
get_table_bloat
```

These tools must **not** use the application's main database credentials.

Instead, they use:

```text
devops_agent_readonly
```

This is a dedicated PostgreSQL read-only role.

The database connection is environment-specific.

For example:

```text
RDS Agent
    │
    ├── DEV
    │     └── DEV RDS
    │           └── devops_agent_readonly
    │
    ├── STAGING
    │     └── STAGING RDS
    │           └── devops_agent_readonly
    │
    └── PRODUCTION
          └── PRODUCTION RDS
                └── devops_agent_readonly
```

The agent uses the database configuration for the environment associated with the event.

The read-only role setup is documented separately in:

```text
documentation/rds-agent/readonly-db-role-setup.md
```

---

# 14. MCP Tool Timeouts

MCP calls are protected by a timeout.

The timeout logic is located in:

```text
config/reliability/mcp_timeouts.py
```

The current timeout is:

```text
30 seconds
```

This prevents a slow AWS API call or database connection from keeping the worker stuck forever.

For example:

```text
RDS Agent
    │
    ▼
MCP Tool
    │
    ├── responds within 30 seconds → continue
    │
    └── takes too long → timeout
```

MCP tools return their results as text.

The RDS agent uses:

```text
_parse_mcp_result
```

to process those results.

The parser supports both:

```text
JSON data
```

and:

```text
plain text
```

This is important because not every MCP response is guaranteed to be JSON.

# 16. Step 10 — Find Similar Incidents

The next step is:

```text
retrieve_similar_incidents
```

This step does not use an LLM.

It searches previous incidents using vector similarity.

The current configuration is:

```text
k = 3
fetch_k = 20
lambda_mult = 0.7
```

The vector store uses PostgreSQL/PGVector.

More details are documented separately in:

```text
documentation/rag/pgvector-retrieval.md
```

The purpose is to give the RDS agent historical context.

For example:

```text
Current alarm
     │
     ▼
Vector Search
     │
     ▼
Similar past incidents
     │
     ▼
Additional context for diagnosis
```

---

# 17. Current Retrieval Limitation

At the moment, every previous incident can potentially be used as supporting evidence.

That means an incorrect historical diagnosis can also be retrieved.

There is currently no active mechanism to mark an incident as incorrect and exclude it from future searches.

A rejection mechanism was previously implemented but removed because there was no real UI, API, or Slack action that could call it.

This should be revisited when the human-approval workflow is implemented.

---

# 18. Step 11 — Investigate Further

This is the most agentic part of the pipeline.

The node is:

```text
investigate_further
```

Unlike the previous steps, the LLM can decide which tools to use.

The agent receives tools such as:

```text
get_performance_insights_top_sql
explain_query_for_pid
get_replica_lag
get_table_bloat
```

The LLM decides:

* Which tool to call
* Whether a tool is needed
* How many tools to call
* What order to call them in

The flow can therefore look like:

```text
LLM
 │
 ├── call get_performance_insights_top_sql
 │
 ├── analyze result
 │
 ├── call explain_query_for_pid
 │
 ├── analyze result
 │
 ├── call get_table_bloat
 │
 └── produce investigation result
```

This is implemented using a ReAct-style agent.

---

# 19. Investigation Safety Limits

Because the LLM controls the investigation loop, several guardrails are used.

## 19.1 Recursion Limit

The agent has:

```text
recursion_limit = 11
```

This limits the number of agent/tool interactions.

If the limit is reached:

```text
GraphRecursionError
```

is raised.

This prevents the agent from continuing indefinitely.

---

## 19.2 Tool Timeout

Every tool available to the investigation agent is also wrapped with a timeout.

This is different from the timeout used by `gather_context`.

The reason is that:

```text
gather_context
```

calls tools directly.

But:

```text
investigate_further
```

allows the LLM to call tools itself.

Both paths therefore need timeout protection.

---

# 20. Token Budget

The investigation also has a token budget.

The component responsible for this is:

```text
config/reliability/token_budget.py
```

The current default is:

```text
MAX_INVESTIGATION_TOKENS = 20,000
```

The tracker counts the tokens used by the investigation.

If the total exceeds the configured budget:

```text
TokenBudgetExceeded
```

is raised after the investigation completes.

Important:

The token budget currently does **not** stop the LLM in the middle of an investigation.

The recursion limit is what actually limits the investigation while it is running.

The token budget acts as a final cost check before the pipeline continues.

If the budget is exceeded:

```text
investigation
      │
      ▼
TokenBudgetExceeded
      │
      X
diagnose does not run
```

---

# 21. Prompt Injection Protection

The investigation and diagnosis prompts tell the LLM to treat:

* CloudWatch alarm data
* Database data
* MCP tool results
* Historical incident information

as **data to analyze**, not instructions to follow.

This is important because some of the information being analyzed ultimately comes from external systems.

For example, a database field could contain text such as:

```text
IGNORE ALL PREVIOUS INSTRUCTIONS
```

The model should treat that as data, not as an instruction.

Prompt-injection evaluation is covered by:

```text
tests/eval/test_diagnose_eval.py
```

---

# 22. Step 12 — Diagnose the Incident

After the investigation finishes, the pipeline reaches:

```text
diagnose
```

This is the main structured LLM call.

The agent uses:

```python
llm = get_llm().with_structured_output(Diagnosis)
```

The result must match the `Diagnosis` Pydantic model.

The model contains:

```text
title
description
risk_tier
```

The risk tier can be:

```text
low
medium
high
```

This structured output makes the final diagnosis predictable and easier for the rest of the application to process.

---

# 23. Step 13 — Save the Incident

The diagnosis is then saved to the database.

The relevant node is:

```text
persist_incident
```

The system checks whether an incident already exists for the same:

```text
raw_event_id
```

If it already exists, the existing incident is reused.

If it does not exist, a new incident is created.

This is important because Celery can retry the entire pipeline.

Without this check:

```text
First attempt
    │
    ▼
Create incident
    │
    ▼
Slack fails
    │
    ▼
Celery retries
    │
    ▼
Create second incident
```

The idempotency check prevents that.

---

# 24. Incident Embedding

After the incident is saved, it is embedded into PGVector.

The embedding operation is safe to repeat because the vector store uses the incident ID when updating the record.

Therefore, if the first attempt partially succeeds and Celery retries, re-embedding the incident is safe.

---

# 25. Step 14 — Send the Diagnosis to Slack

The final pipeline step is:

```text
notify_slack
```

The system first checks whether this incident has already been sent to Slack.

The logic is:

```text
Is incident already notified?
        │
        ├── YES → Skip Slack
        │
        └── NO
              │
              ▼
        Send Slack message
              │
              ▼
        Mark as notified
```

The database field is:

```text
Incident.notified_at
```

It remains `NULL` until the Slack message is successfully sent.

This ordering is important.

The system must **not** mark the incident as notified before sending the message.

Otherwise:

```text
Mark as notified
      │
      ▼
Slack send fails
      │
      ▼
System thinks Slack was already notified
      │
      ▼
No retry notification
```

The current implementation avoids that problem.

# 27. Where the Logs Go

There are two main log files.

## `logs/app.log`

Contains logs from the FastAPI/Uvicorn process.

Examples:

* Application startup
* Application shutdown
* HTTP requests
* Webhook processing

---

## `logs/jobs.log`

Contains logs from the Celery worker and the RDS MCP server.

Examples:

* Celery jobs
* RDS agent nodes
* MCP calls
* Database diagnostic calls
* LLM calls
* Investigation logs

The MCP server runs as a separate process, so it does not automatically inherit the Celery logging configuration.

The MCP process receives:

```text
LOG_FILE_NAME=jobs.log
```

so it writes to the same jobs log.

Both log files use:

```text
ConcurrentRotatingFileHandler
```

The current configuration rotates logs at:

```text
50 MB
```

This prevents the log files from growing indefinitely.

The configuration is located in:

```text
config/logging.py
```

# 29. Celery Does Not Auto-Reload

FastAPI can use:

```text
uvicorn --reload
```

to automatically reload application changes.

Celery does not automatically reload.

After changing Celery-related code, restart the worker.

For example:

```bash
python -m celery -A config.celery_app worker --loglevel=info
```

Otherwise, the worker may continue running old code.

# 30. What Happens When an Alarm Resolves?

CloudWatch sends another SNS notification when an alarm changes from:

```text
ALARM
```

to:

```text
OK
```

This is a new event.

It goes through the same pipeline:

```text
CloudWatch
    │
    ▼
SNS
    │
    ▼
Webhook
    │
    ▼
raw_events
    │
    ▼
Celery
    │
    ▼
RDS Agent
```

Currently, the `ALARM` and `OK` events create separate incident records.

For example:

```text
ALARM
  │
  └── Incident A

OK
  │
  └── Incident B
```

They are currently not directly linked in the database.

The model contains:

```text
Incident.resolved_at
```

but the current pipeline does not use it to connect the two incidents.

# 31. Current Limitations

The current implementation has several known limitations.

## 31.1 ALARM and OK incidents are not linked

An alarm and its recovery currently create separate incidents.

There is no automatic relationship between them.

---

## 31.2 GraphRecursionError is currently retryable

If the investigation reaches the recursion limit:

```text
GraphRecursionError
```

is raised.

Currently, this falls into the generic retry path.

This means the same investigation may be attempted again and may hit the same limit.

It may be better to classify this as non-retryable in the future.

---

## 31.3 Historical Incident Retrieval Can Be Wrong

The RDS agent currently uses previous incidents as supporting evidence.

A previous incorrect diagnosis can therefore influence a future diagnosis.

A proper incident-rejection workflow should be added when the human approval workflow is introduced.

---

## 31.4 Some Incident Statuses Are Not Currently Used

The model contains statuses such as:

```text
awaiting_approval
resolved
diagnosing
```

but the current pipeline does not actively transition incidents through these states.

Currently, incidents remain at the default status.

This is expected to change when the human-in-the-loop workflow is implemented.

---

## 31.5 Token Budget Does Not Stop the Investigation Immediately

The token tracker counts usage, but it does not currently stop the LLM in the middle of the investigation.

The actual mid-investigation limit is:

```text
recursion_limit
```

The token budget is enforced after the investigation finishes.

---

## 31.6 Rate Limits Are Independent

There are two separate rate limits:

```text
Webhook rate limit
Celery task rate limit
```

They protect different parts of the system and do not share a combined usage view.

---

## 31.7 Deployment Topology Is Not Covered

The codebase currently supports:

```text
FastAPI
Celery Worker
MCP Server
```

as separate processes.

The intended production architecture may deploy the API and Celery worker as separate services.

That deployment configuration is outside the scope of this document.

# 32. Important Design Principles

The current RDS diagnosis pipeline follows several important principles.

### Keep the webhook fast

The webhook should only:

```text
Receive
Validate
Store
Queue
Return
```

It should not run the diagnosis itself.

---

### Keep database access read-only

The RDS Agent uses:

```text
devops_agent_readonly
```

for database diagnostics.

The agent should never use application superuser credentials for read-only investigation.

---

### Keep routing deterministic

The supervisor decides which agent handles an event using deterministic rules.

The LLM is not responsible for deciding which domain agent should run.

---

### Limit LLM autonomy

The investigation agent can choose tools, but it is constrained by:

```text
Tool timeouts
Recursion limit
Token budget
Prompt injection protection
```

---

### Make retries safe

Celery can retry the complete pipeline.

Therefore:

```text
Incident creation
Slack notification
Vector embedding
```

are designed to be safe when repeated.

---

# 33. Summary

The RDS Agent works as follows:

```text
CloudWatch
    ↓
SNS
    ↓
FastAPI Webhook
    ↓
Validate + Store Event
    ↓
Celery Queue
    ↓
Supervisor
    ↓
RDS Agent
    ↓
Gather Database Context
    ↓
Find Similar Incidents
    ↓
LLM Investigation
    ↓
Structured Diagnosis
    ↓
Save Incident
    ↓
Send Slack Notification
```

The key idea is:

> **The webhook receives the event; Celery runs the diagnosis; the RDS Agent investigates the database; the LLM produces the diagnosis; and Slack receives the final result.**

The pipeline is designed so that failures, retries, timeouts, duplicate processing, and excessive LLM usage are controlled rather than allowed to run indefinitely.
